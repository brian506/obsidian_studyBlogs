
## GPS 요청 json

```json
  {
    "latitude": 37.5665,
    "longitude": 126.9780,
    "accuracy": 12.5,
    "battery": 87,
    "speed": 1.4,
    "measuredAt": "2026-08-04T14:23:11Z"
  }
```

## 배터리 잔량 알림 

보호 대상자(WARD) 기기의 배터리가 **보호자가 미리 고른 잔량(%)** 에 도달하면
  보호자·관계자 전원에게 푸시를 보낸다.

### 설정
  - 고를 수 있는 값: **10 ~ 100, 10 단위**
  - **개수 제한 없음** — 여러 개 동시 선택 가능 (예: 50%, 20%)
  - **기본값 없음** — 아무것도 안 고르면 알림이 안 나간다
  - 별도의 **마스터 스위치(ON/OFF)**, OFF면 판정 자체를 안 한다

### 알림이 나가는 조건 (전부 만족해야 함)
  1. 마스터 스위치가 ON
  2. GPS 보고에 배터리 값이 실려 있음
  3. 현재 잔량이 고른 값 **이하**로 내려감 (여러 개 걸리면 **가장 낮은 값** 기준)

  > 판정 시점은 **GPS가 들어올 때마다**. 별도 스케줄러 없음.

### 중복 알림 방지
  배터리는 부하·온도로 1~2% 계속 출렁인다. 그래서 한 번 알린 값은 **다시 알리지 않는다.**
  - **재무장 조건**: 알린 값보다 **5% 넘게 회복**해야 그 값을 다시 알릴 수 있다
  - **더 낮은 값에 도달하면 즉시 알림**
  - 고른 값 범위를 완전히 벗어나면 상태 초기화 / 억제 상태는 **1일** 뒤 만료

### 예시 — 50%, 20% 두 개를 골랐을 때
| 잔량        | 결과           | 이유                        |
| --------- | ------------ | ------------------------- |
| 55%       | 조용           | 아직 도달 안 함                 |
| 48%       | **알림 "50%"** | 50% 도달, 첫 알림              |
| 47% → 44% | 조용           | 이미 50%로 알림                |
| 51%       | 조용           | 55% 미만이라 재무장 안 됨 (출렁임 흡수) |
| 18%       | **알림 "20%"** | 더 낮은 값에 도달                |
| 26%로 충전   | 조용           | 재무장만                      |
| 100%로 충전  | 조용           | 상태 완전 초기화                 |
| 다시 18%    | **알림 "20%"** | 재무장돼 있으므로 다시 알림           |

### 알림 내용
  - 제목 `배터리 잔량 알림` / 본문 `기기 배터리 잔량이 20%에 도달했어요.`
  - 수신자: 해당 피보호자와 연결된 **보호자 + 관계자 전원**
  - 앱 알림함 저장 + FCM 푸시 동시 발송

### 알아둘 점
  - 스위치를 껐다 켜면 이전 억제 상태가 남아 있다 (TTL 1일이라 하루 뒤 해소)
  - 배터리 값을 안 보내는 기기는 이 알림이 아예 동작하지 않는다

## 안심존 진입/이탈 알림
  
보호 대상자(WARD)가 보호자가 등록해 둔 **원형 안심존**에 들어가거나 나가면  
보호자·관계자 전원에게 푸시를 보낸다.  
  
### 설정  
- 안심존은 **중심 좌표 + 반경**의 원. 반경은 **500 / 1000 / 1500 / 2000m** 중 선택  
- **개수 제한 없음** — 여러 개 등록 가능하며 서로 겹쳐도 된다  
- 진입 알림과 이탈 알림에 **각각 별도 스위치**, OFF면 그 방향 알림만 안 나간다  
  
### 판정이 도는 조건 (전부 만족해야 함)  
1. GPS 정확도(`accuracy`)가 **100m 이하** — 값을 안 보내는 기기는 통과시킨다  
2. 그 WARD에게 등록된 안심존이 **1개 이상**  
3. 직전 판정 기록이 **존재** (최초 관측은 기준선만 세우고 조용)  
  
> 판정 시점은 **GPS가 들어올 때마다**. 별도 스케줄러 없음.  
  
---  
  
### 핵심 원리 — 상태가 아니라 "변화"를 알린다  
  
GPS가 알려주는 건 **"지금 어디"** 뿐이다. 알림이 필요한 건 **"방금 무엇이 바뀌었나"** 다.  
  
```  
GPS가 주는 것    "지금 집 안에 있음"      ← 상태. 머무는 내내 참  
알림이 필요한 것  "방금 집에 들어왔음"     ← 변화. 한 순간만 참  
```  
  
집에 1시간 있으면 "집 안에 있음"은 GPS 120번 내내 참이다. 그때마다 알리면 안 된다.  
그래서 **직전 상태를 저장해 두고 지금과 비교**한다. 틀린그림찾기와 같다.  
  
### 비교하는 두 장의 스냅샷  
  
| | 무엇 | 어디서 |  
|---|---|---|  
| `currentKeys` | 지금 좌표가 포함되는 안심존 키 집합 | 방금 계산 |  
| `previousKeys` | 직전 GPS 때 계산했던 집합 | `safe_zone_states` 테이블 |  
  
담기는 건 좌표가 아니라 **안심존 이름표(`safeZoneKey`)** 다.  
그리고 `currentKeys`는 **가진 존 전부가 아니라 지금 안에 있는 존만** 담는다.  
전부 담으면 항상 같은 값이라 변화가 영영 안 잡힌다.  
  
```  
등록된 존   [집, 병원, 복지관]     ← DB에서 전부 조회  
지금 위치   집 안  
currentKeys {집}                  ← contains()가 true인 것만  
```  
  
### 차집합 두 방향  
  
`difference(source, exclude)`는 **source에서 exclude에 있는 걸 지운다.**  
결과는 항상 **첫 번째 인자에만 있는 것**이고, 두 번째는 지울 목록일 뿐 결과에 안 나온다.  
  
| 호출 | 기준 | 남는 것 | 의미 |  
|---|---|---|---|  
| `difference(현재, 과거)` | 현재 | 현재에만 있는 것 | **진입** |  
| `difference(과거, 현재)` | 과거 | 과거에만 있는 것 | **이탈** |  

  
**공통 원소는 양쪽 계산에서 모두 지워진다.** 그래서 "계속 안에 있는 존"은 어느 알림에도 안 잡힌다.  
이게 반복 알림을 막는 장치다.  
  
---  
  
### 예시 — 집(A) 하나만 등록했을 때  
  
| 상황 | 과거 | 현재 | 진입 | 이탈 | 결과 |  
|---|---|---|---|---|---|  
| 밖에서 걷는 중 | `{}` | `{}` | `{}` | `{}` | 조용 |  
| **집 도착** | `{}` | `{A}` | `{A}` | `{}` | **알림 "집에 도착"** |  
| 집에서 쉬는 중 | `{A}` | `{A}` | `{}` | `{}` | 조용 (공통이라 소거) |  
| 집에서 쉬는 중 | `{A}` | `{A}` | `{}` | `{}` | 조용 |  
| **집에서 나감** | `{A}` | `{}` | `{}` | `{A}` | **알림 "집을 벗어남"** |  
  
### 예시 — 집(A)·병원(B)이 겹칠 때  
  
| 상황 | 과거 | 현재 | 진입 | 이탈 |  
|---|---|---|---|---|  
| 겹친 구역 진입 | `{}` | `{A,B}` | `{A,B}` | `{}` |  
| 병원 쪽만 벗어남 | `{A,B}` | `{A}` | `{}` | `{B}` |  
| 둘 다 벗어남 | `{A}` | `{}` | `{}` | `{A}` |  
  
두 번째 줄이 차집합의 진가다. A는 계속 안에 있으므로 **재진입 알림이 안 나가고**, 벗어난 B만 이탈로 잡힌다.

### 상태 저장  
- `safe_zone_states` 테이블, WARD당 1행 (`ward_member_key` UNIQUE)  
- `safe_zone_keys`는 쉼표로 이어붙인 CSV  
- **행 없음 = 최초 관측**(알림 안 함), **빈 문자열 = 존 밖**. 이 둘을 반드시 구분해야 한다  
- 읽기와 쓰기를 한 트랜잭션(`replaceAndGetPrevious`)으로 묶는다.  
  저장이 실패하면 롤백되어 알림도 안 나간다 — 저장 없이 알림만 나가는 경로를 구조적으로 없앴다  
  
### 알림 내용  
- 제목 `안심존 진입 알림` / `안심존 이탈 알림`  
- 본문 `집에 도착했어요.` / `집을(를) 벗어났어요.`  
- 수신자: 해당 피보호자와 연결된 **보호자 + 관계자 전원**  
- 앱 알림함 저장 + FCM 푸시 동시 발송  


### 안심존 목록을 캐싱하지 않는 이유

**1. GPS 핫패스가 아니다**  
`SafeZoneDetectionListener.onGpsSaved`는 `@Async("broadcastExecutor")`, 가상 스레드에서 돈다.  
GPS POST 응답은 이미 나간 뒤다. 커밋 `7d4966d`(#116)에서 핫패스의 불필요한 쿼리를 걷어냈지만  
이 조회는 애초에 그 바깥이라, 캐싱해서 줄일 지연이 사용자에게 안 보인다.  
  
**2. 정합성이 지연보다 비싸다**  
안심존 이탈은 유실되면 안 되는 알림이다
TTL 10분 캐시를 두면 보호자가 존을 옮기거나 지운 뒤 **최대 10분간 옛 기준으로 판정**한다  
→ 없는 존에서 이탈 알림이 나가거나, 실제 이탈을 놓친다.  
evict를 걸어도 CRUD 4곳(`register` / `update` / `delete` / 탈퇴 시 `deleteByWardMemberKey`)을  
전부 정확히 덮어야 하고, 한 곳만 빠지면 그대로 오알림이다.  
  
> `publishTransitions`의 `zone == null` 방어는 존 삭제 상황을 이미 상정한 코드다.  
> 캐시를 넣으면 이런 방어가 더 필요해진다.  
  
**3. 아낄 게 별로 없다**  
`ward_member_key` 인덱스 단일 조회에 WARD당 몇 건. 1,000명 × 30초 주기 = 약 33 QPS.  
Redis는 EC2 내부 컨테이너, RDS는 외부라 왕복이 더 길긴 하지만(대략 0.2ms vs 1~3ms),  
**비동기 경로에서 2ms 절약하려고 무효화 지점 4개를 떠안는 거래**다.  
  
요약하면 — 저지연이 필요 없는 경로에서, 절감폭은 ms 단위인데 대가는 오알림 리스크. 그래서 안 했다.
  
---  
  
### 알아둘 점  
- **정확도가 나쁜 구간에서는 판정 자체가 멈춘다.** 상태를 갱신하지 않고 빠져나가므로,  
  정확도가 회복되면 마지막으로 신뢰할 수 있었던 상태와 비교된다. 알림이 늦게라도 나간다  
- **겹친 존에 동시에 들어가면 알림이 존 개수만큼 나간다.** 반경이 최소 500m라 도심에서는 겹치기 쉽다  
- **존을 새로 만들거나 반경을 바꾸면 이동 없이 알림이 나갈 수 있다.**  
  `previousKeys`는 옛 설정 기준, `currentKeys`는 새 설정 기준이라 비교의 전제가 깨진다.  
  현재 코드는 존 *삭제*만 방어하고 *수정*은 방어하지 않는다  
- **마지막 존을 지우면 이탈 알림 없이 끝난다.** 상태만 삭제하고 판정을 건너뛴다  
- **경계선에 서 있으면 진입·이탈이 반복될 수 있다.** GPS 오차로 판정이 오가는데,  
  매번 실제로 상태가 바뀌므로 차집합은 정상 전이로 본다. 막으려면 히스테리시스가 따로 필요하다  
- 안심존 목록은 **캐싱하지 않고 GPS마다 DB를 조회**한다. 핫패스가 아니고, TTL 캐시는 존 수정 후 오알림을 낸다
