
## GPS값을 어떻게 Rule-based 컨테이너로 전달할까?(단일 or 배치)

### GPS 값 전달 과정
**GPS값이 들어왔을 때**
1. DB, Redis 저장
2. Redis에서 최근 n개의 위치값을 읽어서 input_data 생성
	- n점을 읽는 이유는 안심존에서의 이탈을 더 정확히 판별하기 위함(GPS 신뢰도)
3. input_data를 SQS로 전송

input_data 예시
```json
  {
    "user_id": "...",
    "current_location": { ...현재 점... },
    "recent_locations": [ ...최근 N점... ],
    "safe_zones": [ ... ],
    "settings": { ...사용자 설정 DTO... },
    "evaluation_time": "..."
  }
```

**n을 몇으로 해야하나?**

## 이상 조건 알림 mvp
### 기기 상태 감지 (배터리 + 오프라인)

####  상태 3종
 `ONLINE` · `LOW_BATTERY` · `OFFLINE`

#### 판정 기준
  - **배터리 부족**: 배터리 ≤ 20%
  - **오프라인**: 마지막 기록 이후 공백이 임계치 초과
      - 수집 주기 30초~2분 → **10분** 초과 시
      - 수집 주기 3~5분 → **15분** 초과 시
  - 우선순위: **오프라인 판정 > 배터리 판정** (공백 초과면 배터리 값 무시)

#### 알림 원칙 (단 하나)
  > **상태 전이(new ≠ prev)일 때만 1회 알림. 같은 상태 반복이면 무음.**

  ## 처리 흐름
  ```
  서버 (스케줄러 or GPS 수신 이벤트)
    → SQS: { currentState, 마지막 기록 시각, 수집 주기, battery }
    → Python 룰엔진: 새 상태 계산
        - new ≠ prev → 결과 SQS로 { previous, new, detected_at } 전송
        - new == prev → None (아무것도 안 보냄)
    → 서버: 상태 갱신 + FCM 푸시
  ```


### 오프라인 감지 스케줄러 — Redis 데드라인 타이머

  전체 기기를 주기적으로 풀스캔하지 않는다. **기기별 one-shot 타이머**를 Redis ZSET으로 관리한다.

#### ① 타이머 무장 (arm) — GPS 수신 시
  GPS 저장 트랜잭션 커밋 후 비동기 리스너(`@TransactionalEventListener AFTER_COMMIT`)가:
  1. 마지막 포인트를 Redis에 저장 (`device:lastpoint:{memberKey}`, TTL 60분)
  2. ZSET(`device:offline:deadline`)에 **데드라인 = 마지막 기록 시각 + 임계치(10분/15분)** 등록
     → GPS가 계속 오는 한 데드라인이 계속 미래로 밀림 (타이머 리셋)
  3. 동시에 SQS로 즉시 발행 → 룰엔진이 배터리 부족 / 온라인 복귀 판정

#### ② 타이머 발화 — 스케줄러 스캔
  - `@Scheduled(fixedDelay = 60초)` — `device.offline.scan-delay-ms`로 조정 가능, prod/dev 프로파일만 동작
  - 매 스캔마다:
    1. ZSET에서 **데드라인 ≤ 현재 시각**인 memberKey만 조회 (due인 기기만, 풀스캔 없음)
    2. 마지막 포인트 + 수집 주기를 실어 SQS 발행 → 룰엔진이 공백 계산해 OFFLINE 판정
    3. **disarm** (ZSET에서 제거) → 타이머당 발행은 딱 1회

#### 케이스 정리

| 케이스        | 전이                    | 트리거          | 판정               | 알림  |
| ---------- | --------------------- | ------------ | ---------------- | --- |
| 배터리 부족 진입  | ONLINE → LOW_BATTERY  | GPS 수신       | battery ≤ 20%    | 🔔  |
| 오프라인 진입    | LOW_BATTERY → OFFLINE | 스케줄러         | 공백 12분 ≥ 기준 10분  | 🔔  |
| 오프라인 지속    | OFFLINE → OFFLINE     | 스케줄러 재전송     | 전이 없음            | 🔇  |
| 복귀         | OFFLINE → ONLINE      | GPS 수신 (이벤트) | 공백 0, battery 정상 | 🔔  |
| 긴 주기 오탐 방지 | ONLINE → ONLINE       | 스케줄러         | 공백 12분 < 기준 15분  | 🔇  |

#### 핵심 포인트
  - **진입/복귀 각 1회만 알림** — 오프라인 1시간 지속돼도 알림은 진입 시점 1번뿐
  - **오프라인 감지는 스케줄러(폴링), 복귀 감지는 GPS 수신(이벤트 드리븐)** — 꺼진 기기는 이벤트를 못 보내므로
  - **수집 주기별 임계치 차등** — 5분 주기 기기의 12분 공백은 정상이라 오탐하지 않음
- **순서 보장** - SQS FIFO가 아닌, GPS 수신 시간으로 계산
