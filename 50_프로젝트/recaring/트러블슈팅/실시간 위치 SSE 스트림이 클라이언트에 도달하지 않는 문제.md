## 문제 상황

- 보호자 앱 홈에서 보호 대상자의 실시간 이동 경로가 보이지 않음
- /location/stream/{wardKey} 요청 로그는 뜸
- 서버의 SseEmitter (스트림 수명) : 300초
- nginx proxy_read_timeout : 업스트림이 조용하면 끊는 시간 
- GPS 한개  이벤트 크기 : 141B

## Nginx

### GET /location/stream/{wardKey}

**연결 과정**
1. client가 GET 요청
2. 서버 -> client에게 200 ok를 응답하고 새로운 연결이 생성되는게 아니라, 이때부터 통로 계속 연결
	- nginx는 연결 시 upstream 커넥션을 잡고 있어야함

### 리버스 프록시인 Nginx가 서버의 응답을 처리하는 방법

#### 버퍼링이 무엇인가?
> 속도가 다른 두 지점 사이에 놓는 임시 저장 공간

- 리버스 프록시인 Nginx는 서버와 같은 네트워크 상에 있음
	- 그래서 Nginx와 서버는 네트워크 지연이 없음
- Client와는 다른 네트워크 상에 있으므로,
	- 백엔드 응답을 Nginx 메모리에 최대한 빨리 다 받음
	- 다 받으면 백엔드와의 커넥션을 끊고, Client에게 천천히 응답

이와 같은 이유로 **Nginx는 기본적으로 `proxy_buffering on` 상태** 
- 기본값 4KB가 모여야 flush
#### nginx의 flush(client에게 전송) 기준

1. 버퍼 하나가 가득 찼을 때
2. 업스트림 응답이 끝났을 때

## 원인 분석

기본 값으로 버퍼링이 on 되어있으면 Nginx는 4KB가 모이고 나서 client에게 flush한다.
그리고 이 연결에서 버퍼링에서 최대 모아지는 데이터양은 5분에 1.6KB이다.(30초마다 GPS값 송신)

이 버퍼링의 기본값은 한 사용자에게 받는 양이다.

#### 화면에서 실시간 경로가 보여지지 않는 이유
-> Nginx에서 4KB 크기의 데이터양이 모아지지 않아서 

1. Nginx는 가만히 있음
2. SSE의 연결 타임 아웃은 300초
3. 연결 타임 아웃 시간 안에 아무런 GPS를 받지 못함
4. 화면에 위치값 전달 안돼서 보여지지 않음
5. 300초에 응답이 종료되면서 1.6KB가 뒤늦게 한꺼번에 flush. 다만 클라이언트가 그전에 read timeout으로 끊었다면 그마저도 못 받음

## 해결 방법

### 1. 버퍼링 off

```java
location /api/v1/location/stream/ { # ← 이 경로에만 
	proxy_buffering off; 
}
```

- 버퍼에 모아서 보내지 않고 오는 값마다 바로 보낸다.
- 일반 REST API들엔 버퍼링을 켜둬야 함

#### 버퍼링 끄면 비효율적인거 아닌가?

**결론** : SSE에서는 버퍼링을 켜도 백엔드와의 연결이 끊기는게 아니기 때문에, 버퍼링을 꺼도 추가 비용이 없다.
##### 버퍼링을 써야하는 상황
**일반 REST**:  백엔드 1ms 만에 200KB 다 뱉음 → nginx가 다 받음 → 백엔드 커넥션 close
            → 이후 30초 동안 느린 클라이언트를 nginx가 혼자 상대
            
##### 버퍼링 써도 효과 없는 상황
**SSE**:  백엔드가 300초 동안 조금씩 뱉음 → nginx는 300초 내내 업스트림 커넥션을 잡고 있어야 함
      → 버퍼링을 켜든 끄든 백엔드 커넥션 유지 시간은 똑같이 300초

#### 버퍼링을 끄면 생기는 부작용

1. **syscall 증가** : 141B 이벤트마다 write를 하니 4KB 모아서 한 번 쓰는 것보다 syscall이 많아짐
2. **백프레셔가 업스트림까지 전파됨.** 버퍼가 없으니 클라이언트가 느리면 → nginx 소켓 send 버퍼가 참 → nginx가 업스트림에서 읽는 걸 멈춤 → 백엔드의 write가 블로킹되거나 실패

### 2. proxy_read_timeout

서버에서 SSE 스트림 연결을 끊어주는 5분보다 살짝 더 큰 값인 6분정도로 설정

### 3. 앱에서 홈 화면 갱신

사용자가 만약에 5분 넘게 모니터링 한다면?
- 값이 잘 들어와도 5분이 넘으면 SSE 연결이 끊기기 때문에, 앱에서 다시 재요청 로직이 필요


## 이외의 설정해야할 것들

`proxy_http_version 1.1`

- 왜 HTTP/1.1인가
	- chunked streaming / keep alive에 필요

- **왜 HTTP/2는 안했나**
	- 보호자 한 명이 **동시에 여러 피보호자**를 지켜보면, 그 기기에서 스트림이 여러 개 열린다. OkHttp 기본값 기준 5개를 넘으면 6번째는 큐에서 대기한다.
	- HTTP/2.2는 연결 하나에 멀티플렉싱이 가능해 연결이 다수가 가능함.
		-> 이건 나중에 정책이 바꾸거나 병목이 생길때 2.2로 전환하자

`proxy_set_header Connection "";`

- 클라이언트 -> Nginx : Keepalive 정상임
- Nginx -> 웹 서버 : **nginx는 업스트림에 `Connection: close`를 붙여 보내는 게 기본**. `proxy_http_version 1.1`로 올려놔도 이 헤더가 그대로 가면 keep-alive가 무력화
	-> SSE 연결이 Nginx에서 웹서버에서도 **Keepalive(연결 파이프라인 유지) 지속하기** 위해서 설정
