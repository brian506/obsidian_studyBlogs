### ElastiCache 도입 배경

기존에 ECS 컨테이너로 Redis를 띄웠을 때는 전부 유실돼도 괜찮은 데이터를 사용하고 있었다.
리프레시 토큰, sms 토큰 모두 db를 읽고, 최신 위치값 등들도 다시 새로 받으면 그만인 값이었다. 이상탐지 파이프라인을 구축하고 나서 EC2에 종속되는 Redis 컨테이너가 EC2가 다운됐을 때 탐지 흐름이 멈추게된다.
따라서 이상탐지 결과의 알림 전송 보장, 실시간 GPS 수신, 자동 페일오버(SPOF 극복)를 보장 받기 위해 전환하게 되었다. 

### ElastiCache 설정

- 앱 내의 VPC 안에 설정
- Replica 1개 + Multi-AZ 자동 페일오버 활성화 (SPOF 제거)
- 파라미터 그룹 설정
	- maxmemory-policy : 메모리 꽉 찼을 때 어떤 키를 지울지
		- stream이 삭제되지 않도록 noeviction 설정
	- notify-keyspace-events : 키 만료 삭제 시 이벤트 발행 여부
		- TTL 만료시 이벤트 기반으로 처리하기 위해 설정
	- timeout : 유휴 클라이언트 연결 끊는 시간


### 학습 컨테이너 스펙 결정

#### 처음에 고려한 방식 -  EC2(spot) + ASG + EventBridge
- EventBridge가 EC2 spot 인스턴스의 컨테이너를 트리거해서 하루에 한번만 실행시켜 학습할 계획이었다.
	- Isolation Forest는 sklearn 기반 CPU 알고리즘이라 GPU 제약이 없다.
	- EC2를 쓰면서 결정해야할 정책이 너무 많기 때문에 유지보수에 어려움이 있을 수 있다.
	
#### 최종 결정된 방식 - ECS fargate + EventBridge
- GPU 없이 CPU만 필요한 알고리즘 기법이어서 fargate가 적합하다.
- 태스크가 실제로 쓴 vCPU-초 / 메모리-초 단위로 실행됨
- EC2 스팟 인스턴스보단 비싸지만 큰 차이는 없음

### S3 설정

키 구조 : memberKey 고정 키 + S3 버저닝
- `isolation-forest/{memberKey}/model.pkl`
- 매 학습마다 새로운 날짜 파일을 만드는게 아니라 버져닝을 통해서 덮어쓴다.
- 특정 날짜를 정해서 탐색하는게 아니라 매번 같은 경로만 읽으면 된다.
