## 1. 문제 상황

SSE 부하 테스트(TS-02) 과정에서 앱 태스크 메모리를 **1024 → 2048**로 올렸다.
그 직후 롤링 배포가 실패하기 시작했다.

```
unable to place a task because no container instance met all of its requirements.
The closest matching container-instance ... has insufficient memory available.
```

`free -m`상으로는 available이 2GB 넘게 남아 있었다.

---

## 2. 원인 ① — ECS 배치는 OS 여유 메모리가 아니라 '예약' 기준이다

| 태스크 | 예약 | 실사용 |
|---|---|---|
| app (구버전) | 2048 | 626 |
| Redis | 512 | 4 |
| 모니터링 | 1024 | ~173 |
| **합계** | **3584** / 인스턴스 등록 ~3700 | — |

남은 예약이 **약 150MiB**. 신버전(1024 예약)을 올릴 자리가 없다.
`free -m`의 available과 ECS의 배치 가능량은 다른 값이었다.

## 3. 원인 ② — 무중단은 본질적으로 N+1 용량을 요구한다

무중단 배포의 정의가 "신버전이 healthy해진 뒤 구버전을 내린다"이므로, 신·구 두 벌이 **잠깐 반드시 공존**한다.
따라서 단일 박스라면 **앱 1벌분 메모리를 항상 비워둬야 한다.** 전체 메모리를 앱 하나에 다 줄 수 없다.

| 2벌을 어디에 두나 | 비용 |
|---|---|
| 같은 인스턴스 | 앱 2벌분 메모리가 상시 필요 |
| 다른 인스턴스 | 배포 때만 임시 인스턴스 (ASG scale-out) |

→ 후자를 택해 **ASG를 도입**했다.

---

## 4. ASG의 함정 — "자동 반납"은 없다

ECS managed scaling은 **scale-out과 빈 인스턴스 종료**는 자동이지만,
**돌고 있는 태스크를 더 적은 인스턴스로 다시 모으는(consolidate) 동작은 하지 않는다.**

> "상시 1대 + 배포 때만 임시 1대 → 끝나면 자동 반납"은 ECS의 결을 거스르는 구조였다.
> 반납하려면 명시적 drain(수동 또는 파이프라인 자동화)이 필요하고,
> 메인 인스턴스가 ASG 라이프사이클에 들어가면 **Redis 캐시 영속성까지 위협**받는다.

### 되돌리는 과정에서 만난 것들

| # | 막힌 지점 | 내용 |
|---|---|---|
| 1 | `maximumPercent ≤ 100` 거부 | `InvalidParameterException: Availability Zone Rebalancing does not support maximumPercent <= 100%` → AZ 리밸런싱을 함께 비활성화해야 한다 |
| 2 | `min=0`만 바꾸면 안 됨 | `max=200`이 남아 있으면 ECS가 신버전을 먼저 띄우려다 capacity provider scale-out을 유발 → **없애려던 ASG가 다시 깨어난다.** `min=0` + `max=100`이 한 세트 |
| 3 | launch type은 태스크 정의가 아니다 | 태스크 정의는 처음부터 `requiresCompatibilities: [EC2]`였다. 바뀐 건 **서비스의 실행 방식**(`launchType` ↔ `capacityProviderStrategy`)이고, 되돌리려면 **서비스 재생성**이 필요하다 |
| 4 | 좀비 서비스 | 서비스를 재생성했더니 옛 서비스가 `desired=0` + 이미 삭제된 ASG의 capacity provider에 묶인 채 잔존 |
| 5 | 파이프라인이 좀비를 가리킴 | `deploy.yml`이 옛 서비스명을 타겟으로 남아 다음 배포가 빈 서비스에 적용됨 |

---

## 5. 숨은 두 번째 천장 — ENI

t3.medium은 **ENI 3개** 한도다.

```
awsvpc 앱 태스크 1개당 ENI 1개 + 호스트 primary 1개
롤링 중 앱 2벌 → 2 + 1 = 3 = 정확히 한계
```

(Redis·모니터링은 bridge 모드라 ENI를 소비하지 않아 가능했다.)
**메모리뿐 아니라 ENI도 오버랩 구간엔 여유가 0**이었다. 인스턴스 타입 선택이 배포 전략의 상한을 결정한다.

---

## 6. 진짜 원인 — 인프라가 아니라 앱 메모리였다

단일 박스 롤링이 원래 잘 돌던 건 앱이 **~1024이던 시절**이라 `2 × 1024`가 박스에 들어갔기 때문이다.
부하 테스트를 하며 앱을 **2048로 올린 것**이 단일 박스 fit을 깨뜨렸고, 그게 ASG 우회의 발단이었다.

### right-size

| 태스크 | 조정 | 근거 |
|---|---|---|
| app | 2048 → **~1152–1280** | 실사용 626 + 여유 |
| 모니터링 | 1024 → **~512–640** | 실사용 173 (Grafana 122 / Prometheus 32 / exporters 18). Prometheus는 히스토그램 카디널리티 고려해 여유 확보 |
| Redis | **512 유지** | 실사용 4MiB지만 **재시작 시 캐시 소실이 하드 제약**이라 줄일 수 없다. 과할당이 '동결'된 케이스 |

**첫 전환 1회만 짧은 다운이 필요했다.** 돌고 있는 구버전이 2048이라 축소 버전과 동시 배치가 불가능했기 때문이다(`2048 + 신버전 + Redis + 모니터링 > 등록 메모리`). 이후 작은 사이즈끼리는 무중단 롤링이 복원됐다.

---

## 7. 최종 구조

```
t3.medium 1대 (app + Redis + 모니터링 동거), ASG 없음
launchType = EC2
롤링 배포  min=100% / max=200% + Deployment Circuit Breaker
nginx      별도 t3.nano
```

**ASG는 문제의 우회로였을 뿐, 답이 아니었다.**

---

## 8. 교훈

1. **ECS 배치는 예약 기준이다.** `free -m`의 available ≠ 배치 가능량. 실측 기반 right-size를 하지 않으면 용량을 낭비하고 배포가 막힌다
2. **무중단은 N+1 용량을 요구한다.** 단일 박스라면 앱 1벌분을 항상 비워둬야 한다
3. **ECS managed scaling은 모으지 않는다.** "임시 인스턴스 자동 반납"은 환상이다
4. **콜드 스타트를 실측하라.** "몇 초"라 가정했지만 실제는 ~100초였다
5. **상태 있는 사이드카가 전략 전체를 제약한다.** 재시작이 곧 데이터 손실이면 그 태스크의 과할당은 줄일 수 없다
6. **서킷브레이커 + `min=100%`가 안전망이었다.** 이 모든 실험 내내 실패한 배포가 구버전을 죽이지 않아 **다운타임 0이 유지**됐다
