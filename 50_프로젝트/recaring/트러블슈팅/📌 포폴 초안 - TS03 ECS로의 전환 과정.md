## 1. ECS로의 전환 이유

기존에는 하나의 EC2 안에서 서로 다른 포트를 가진 두 개의 컨테이너를 띄우고, Blue-Green 전환 로직을 셸 스크립트로 직접 작성해 운영했습니다. 스크립트가 빈 포트를 탐색해 새 컨테이너를 띄우고, 30초 간격으로 최대 12회까지 헬스체크를 수행한 뒤, nginx의 upstream 설정 파일을 다시 쓰고 reload하는 방식이었습니다.

이 방식은 운영 기간 동안 지속적인 수정을 요구했습니다. **배포 스크립트를 9회 수정했고, 그중 4회가 hotfix였습니다.** 헬스체크 대기 시간이 부족해 정상 배포를 실패로 판정한 경우, 경로 설정 오류, SSL 인증서가 아직 발급되지 않은 상태에서 nginx reload가 실패해 파이프라인 전체가 중단된 경우가 있었습니다. 배포 로직이 애플리케이션 코드와 함께 관리되면서, 인프라 변경이 있을 때마다 스크립트를 함께 고쳐야 했습니다.

결정적인 한계는 **롤백 경로였습니다.** 스크립트의 실패 처리는 nginx upstream을 전환하기 **이전** 단계에만 존재했습니다. 헬스체크에 실패하면 새로 띄운 컨테이너를 중지하고 종료하는 것이 전부였고, 이미 트래픽을 새 버전으로 넘긴 **이후**에 장애가 발생하면 되돌릴 방법이 스크립트 안에 없었습니다. 사람이 장애를 인지하고 수동으로 이전 버전을 다시 띄워야 했습니다.

ECS의 Deployment Circuit Breaker는 배포 완료 이후의 헬스체크 실패까지 감지해 직전 태스크 정의로 자동 복귀합니다. **배포 자동화가 아니라 실패 복구 자동화가 전환의 이유였습니다.**

## 2. 배포 방식의 변화 (비교표)

배포 방식은 두 단계가 아니라 세 단계에 걸쳐 바뀌었습니다. 스크립트 방식을 유지한 채 서버 접근 방식을 먼저 개선했고, 이후 배포 로직 자체를 ECS로 넘겼습니다.

| 비교 항목 | 1. SSH + Script | 2. SSM + Script | 3. ECS ✓ |
|---|---|---|---|
| **서버 접근** | SSH 키를 CI Secrets에 보관 | IAM 기반 SSM, 인스턴스 ID를 태그로 동적 조회 | 불필요 |
| 새 컨테이너 생성 | 빈 포트 탐색 후 `docker run` | 동일 | 자동 |
| 헬스체크 | 30초 간격 수동 루프 (최대 12회) | 동일 | `startPeriod` 기반 자동 |
| **롤백** | **전환 전 실패만** 처리 | 동일 | **전환 후 실패도 자동 복귀** |
| 라우팅 갱신 | `service-url.inc` 수정 후 reload | 동일 | Cloud Map 자동 등록 / 해제 |
| **배포 범위** | **전체 스택 일괄 기동** | 동일 | 서비스 단위 독립 |

**1단계에서 2단계로**: CI에서 서버에 접근하기 위해 SSH 키를 GitHub Secrets에 보관하고 있었습니다. 이를 AWS SSM Session Manager 기반의 `send-command` 방식으로 교체하면서 SSH 키와 22번 포트 의존을 제거했고, 인스턴스 ID는 하드코딩 대신 태그(`Name=recaring-app-server`)로 조회하도록 바꿨습니다.

**배포 범위 항목**: 기존 스크립트는 첫 줄에서 redis, nginx, prometheus, grafana, certbot 등 인프라 컨테이너를 모두 함께 기동했습니다. 애플리케이션 하나를 배포하는 작업이 전체 스택을 건드리는 구조였고, 배포 실패가 모니터링과 nginx에까지 영향을 줄 수 있었습니다. ECS로 전환한 뒤에는 서비스 단위로 독립 배포됩니다.

## 3. ALB 없이 ECS에서 무중단 배포를 하기 위해

**제약** — ALB를 도입하면 월 $16의 고정 비용이 발생합니다. MVP 단계의 트래픽 규모에서는 이 비용을 지불할 근거가 부족했습니다. 그런데 ECS에서 공식적으로 지원하는 Blue-Green 배포는 ALB와 CodeDeploy 조합을 전제로 합니다.

**선택** — ALB를 포기하고 Rolling Update와 Cloud Map 서비스 디스커버리 조합으로 전환했습니다. nginx가 Cloud Map DNS(`spring-app.recaring.local`)를 `resolver valid=10s` 설정으로 주기적으로 재조회하므로, 태스크가 교체되어도 nginx 설정을 수정할 필요가 없습니다.

**포기한 것** — 롤백 즉시성입니다. Blue-Green은 타깃 그룹을 전환하는 것만으로 초 단위 복귀가 가능하지만, Rolling Update는 이전 버전의 태스크를 다시 기동해야 하므로 분 단위가 소요됩니다.

**보완** — 롤백 **속도**를 잃은 대신 롤백 **자동화**를 얻었습니다. Deployment Circuit Breaker에 `rollback: true`를 설정해 헬스체크 실패 시 직전 태스크 정의로 자동 복귀하도록 했고, `minimumHealthyPercent 100`으로 새 태스크가 정상 기동한 뒤에만 기존 태스크를 종료하도록 했습니다. 사람이 개입하지 않아도 복구되는 구간을 확보한 것입니다.

**복귀 조건** — 인스턴스를 2대 이상으로 늘리거나 다중 AZ로 확장하는 시점에는 nginx 자체가 단일 장애점이 되므로 ALB로 전환합니다. 그 시점에는 $16이 병목이 아닙니다.

## 4. 문제 상황 — Rolling Update 무중단 배포에서의 포트 충돌

Rolling Update로 방향을 정하자 첫 번째 벽에 부딪혔습니다.

### Rolling Update의 전제 조건

무중단 배포는 신버전이 정상(healthy) 상태가 된 것을 확인한 뒤에 구버전을 내리는 방식입니다. 따라서 V1과 V2가 잠깐이라도 동시에 존재하는 구간이 반드시 필요합니다.

그런데 ECS의 `bridge` 모드는 컨테이너가 EC2 호스트의 네트워크를 공유하기 때문에, 하나의 호스트에서 같은 포트는 단 하나의 컨테이너만 점유할 수 있습니다. 기존 App V1이 호스트의 8080 포트를 잡고 있는 상태에서 새로운 App V2도 8080 포트를 사용하려 하므로, 공존 구간 자체가 성립하지 않습니다.

> 「확인 필요 — 실제로 배포가 어떻게 실패했는지 한 줄 추가.
> 예: 태스크가 PENDING 상태에 머물렀는지, ECS 이벤트에 어떤 메시지가 남았는지.
> 증상이 한 줄 들어가야 '문서로 아는 문제'가 아니라 '겪은 문제'로 읽힌다.」

## 5. 해결 — awsvpc 모드와 Task ENI

`awsvpc` 모드는 컨테이너마다 완전히 독립된 고유의 사설 IP를 가진 ENI(Task ENI)를 부여합니다.

| BRIDGE | AWSVPC |
|---|---|
| **호스트 IP 공유** | **Task ENI 분리** |
| 한 호스트의 같은 포트는 1개 컨테이너만 사용 가능 | 각 컨테이너에 고유 IP, 한 호스트에서 같은 포트 공존 가능 |

App V1이 `10.0.2.30`을 받고 App V2가 `10.0.2.31`을 받아 각각 8080 포트를 엽니다. **IP가 다르기 때문에 하나의 EC2 안에서 포트 충돌이 발생하지 않습니다.**

다만 `awsvpc`는 태스크마다 ENI를 하나씩 소비하며, **이 선택이 이후 두 가지 문제로 이어집니다.** 하나는 태스크 ENI에 Public IP를 할당할 수 없어 외부 통신이 차단되는 문제(TS-04), 다른 하나는 인스턴스 타입별 ENI 개수 한도가 무중단 배포의 상한을 결정하는 문제(TS-05)입니다.

## 6. 전환 결과

배포 로직을 ECS가 관리하게 되면서 스크립트 유지보수가 종료되었습니다. 9회에 걸친 수정과 4회의 hotfix를 발생시켰던 배포 스크립트는 제거되었고, 이후 배포 방식 변경으로 인한 수정은 발생하지 않았습니다.

자동 롤백은 실제 운영에서 검증되었습니다. 이후 인스턴스 확장 실험(TS-05) 과정에서 태스크 배치 실패로 배포가 여러 차례 중단되었으나, **`minimumHealthyPercent 100`과 서킷브레이커가 기존 태스크를 유지한 덕분에 그 기간 내내 서비스 다운타임은 0이었습니다.** 스크립트 방식이었다면 동일한 상황에서 수동 개입이 필요했습니다.

### 남은 비용

배포 소요 시간은 오히려 약 60초 늘었습니다. 대부분은 헬스체크의 `startPeriod 180s`에서 발생합니다. 이는 Spring 애플리케이션의 콜드 스타트(CloudWatch 로그 실측 99.5초)가 완료되기 전에 헬스체크가 실패하는 것을 장애로 오탐하지 않기 위한 안전 마진입니다. 실측 부팅 시간을 기준으로 조정할 수 있는 값이며, 배포 속도 대신 오탐 방지와 자동 복구를 택한 결과입니다.
