

> 전환의 이유, 포기한 것, 그리고 처음에 잘못 짚었던 것들에 대한 기록.

## 한 줄 요약

**인스턴스가 2대 이상이 되는 순간 깨지는 정합성 문제를 해결하기 위해, 인프로세스 이벤트 브로드캐스트를 공유 저장소 기반 폴링으로 바꿨다.** 성능 문제가 아니라 정확성 문제였다.

## 1. 왜 바꿨나

### 결정적 이유 — 멀티 인스턴스에서 동작하지 않는다

기존 구조는 GPS를 수신하면 `ApplicationEventPublisher`로 이벤트를 발행하고, 리스너가 프로세스 내 `Map`에서 해당 ward를 구독 중인 emitter들을 찾아 fan-out하는 방식이었다.

문제는 `ApplicationEventPublisher`가 **JVM 프로세스 내부 이벤트 버스**라는 점이다. ECS task가 2개로 늘어나면 이렇게 된다.

```
WARD 앱   ──ALB──→ task 2 : GPS 수신, task 2 내부에만 이벤트 발행
보호자 앱 ──ALB──→ task 1 : emitter가 task 1의 Map에 등록됨
                            → 이벤트가 영원히 도달하지 않음
```

보호자와 피보호자가 같은 인스턴스에 붙었을 때만 우연히 동작한다. 인스턴스가 2대면 절반, 4대면 3/4이 조용히 실패한다. **에러도 안 나고 로그도 안 남는다.** 화면에 위치가 안 뜰 뿐이다.

이건 튜닝으로 해결되는 성능 문제가 아니라 **경계를 잘못 그은 설계 문제**다. 스케일아웃이 예정된 이상 언젠가 반드시 터지고, 터졌을 때 원인을 찾기 매우 어려운 종류다.

### 부차적 이유 — 요청 워커 점유

`@TransactionalEventListener(AFTER_COMMIT)`는 별도 스레드로 넘어가지 않는다. 트랜잭션 동기화 콜백이라 **커밋한 그 스레드(= GPS POST를 처리 중인 Tomcat 워커)에서 동기 실행**된다. 그래서 fan-out이 끝날 때까지 POST 응답이 반환되지 않았다.

다만 이건 `@Async` 한 줄로 해결된다. **이것만으로는 아키텍처 전환을 정당화하지 못한다.**

> 주의: `@EnableAsync`만 켜고 executor를 지정하지 않으면 Spring은 호출마다 새 스레드를 만드는 executor를 쓴다. bounded 풀을 명시하거나 가상 스레드를 태워야 한다.

### 이유가 아니었던 것 — "쓰기가 보호자 수에 종속된다"

처음에는 이걸 병목으로 적었지만, 숫자를 넣어보면 성립하지 않는다.

정책상 ward당 보호자는 **최대 5명**이다. fan-out은 최대 5회, 각각 소켓 버퍼에 141바이트를 쓰는 작업이다. 마이크로초 단위다.

오히려 전환 후 총비용이 늘었다.

||브로드캐스트|폴링|
|---|---|---|
|비용 발생 시점|GPS 수신 시에만|상시|
|부하테스트 기준|80 POST/s × 최대 5 = 400 send/s|2000 연결 × 1/s = 2000 GET/s|
|아무도 안 볼 때|0|그대로 2000 GET/s|

**유계인 변수(N ≤ 5)를 무계인 변수(연결 수)로 교환한 셈이다.** 이 항목을 전환 사유로 내세우면 안 된다.

## 2. 검토한 선택지

|방식|멀티 인스턴스|상시 스레드|비용 비례 대상|지연|
|---|---|---|---|---|
|인프로세스 브로드캐스트 (기존)|❌|0|이벤트|즉시|
|위 + `@Async`|❌|고정 풀|이벤트|즉시|
|**연결당 폴링 (채택)**|✅|연결 수|**연결 수**|≤ 1초|
|공유 스케줄러 폴링|✅|1|연결 수 (왕복은 1회)|≤ 1초|
|Redis pub/sub|✅|구독자 1~2|이벤트|즉시|
|Redis Streams|✅|구독자 1~2|이벤트|즉시|
|클라이언트 REST 폴링|✅|0|요청|≤ 주기|

핵심 축은 **비용이 이벤트에 비례하느냐, 연결 수에 비례하느냐**다.

### 왜 폴링을 골랐나

Redis pub/sub이 비용 면에서는 더 우수하다. 이벤트 기반이라 헛돌지 않고, 연결당 스레드도 필요 없다. 그럼에도 폴링을 택한 이유는:

- **구독자 생명주기를 관리할 필요가 없다.** pub/sub은 인스턴스 시작 시 구독하고 종료 시 해제해야 하며, 커넥션이 끊기면 재구독 로직이 필요하다. 폴링은 이 전부가 없다.
- **상태가 스레드 지역 변수에 산다.** 마지막 전송값을 루프 안에 들고 있으면 되고, 연결이 끊기면 스레드가 죽으면서 자동 회수된다. 별도 레지스트리를 명시적으로 정리할 코드가 없다.
- **MVP 규모에서 비용 차이가 무의미하다.** 동시 20 연결이면 초당 20회 Redis GET이다. Redis는 초당 10만 건 이상을 처리한다.

즉 **비용이 아니라 구현·운영 단순성을 산 것**이고, 규모가 커지면 재검토할 결정이다. 읽기 경로만 바꾸면 되므로 나중에 옮기는 비용도 크지 않다.

## 3. 무엇을 포기했나

의식적으로 감수한 대가를 명시해둔다.

1. **연결 수에 비례하는 상시 Redis 부하** — GPS가 30초 주기인데 1초마다 조회하므로, 조회 30번 중 29번은 값이 그대로다. 다만 이 낭비의 대가로 "GPS 도착 후 1초 내 화면 갱신"을 얻는다. 30초 주기로 폴링하면 평균 15초 늦게 뜬다. **MVP 규모에서는 이 교환이 유리하다.**
2. **연결당 스레드** — 플랫폼 스레드에서는 확장 한계가 명확하다. 가상 스레드로 흡수할 수 있지만, 근본적으로는 O(N)이다.
3. **최대 1초의 전달 지연** — 이 도메인에서는 무해하다. GPS 자체가 30초 주기이므로 폴링 지연은 전체 지연에 묻힌다.

## 4. 회고 — 잘못 짚었던 것들

이 절이 이 문서에서 가장 중요하다.

### 4-1. 측정한 문제와 적용한 처방의 크기가 맞지 않았다

처음 진단은 "`@TransactionalEventListener`가 워커를 붙잡는다"였고, 여기서 곧바로 push → pull 전환으로 갔다. 하지만 그 진단만 놓고 보면 정답은 `@Async` 한 줄이다.

전환이 정당했던 건 **다른 이유(멀티 인스턴스 정합성) 때문**인데, 처음에는 그걸 인식하지 못한 채 결과적으로 옳은 선택을 했다. 이유를 잘못 짚으면 다음번 판단이 흔들린다.

> 교훈: 처방의 크기가 진단의 크기와 맞는지 먼저 확인한다. 안 맞으면 진단이 불완전한 것이다.

### 4-2. 부하 테스트 중 발생한 장애를 전환의 정당화로 썼다

부하 테스트에서 HikariCP 커넥션 풀 고갈이 관측됐고, 이를 "그래서 가상 스레드가 필요하다"는 근거로 삼았다. 그런데 그 원인인 **2000개의 폴링 스레드는 새 구조에만 존재한다.** 기존 브로드캐스트에는 연결당 스레드가 없었다.

서사를 정직하게 쓰면 이렇게 된다.

> 병목을 고치려고 구조를 바꿨다 → 그 구조가 만든 새 장애가 났다 → 그걸 고치려면 가상 스레드가 필요하다

**자기가 만든 문제를 자기가 푸는 흐름이다.** 원래 구조에 그 문제가 없었다는 걸 아는 사람에게는 설득력이 없다. 새 구조의 대가로 정직하게 기록해야 할 항목이지, 전환의 근거가 될 수 없다.

### 4-3. 메모리 계산이 틀렸다

"플랫폼 스레드 2000개 × 스택 1MB = 2GB"라고 적었는데, **스택 1MB는 가상 주소 공간 예약이지 실제 상주 메모리가 아니다.** `sleep`과 Redis GET만 하는 얕은 콜스택은 실제로 수십 KB만 터치한다. 실측 RSS는 100~200MB 수준이다.

2 vCPU 인스턴스에서 2000 플랫폼 스레드가 힘든 건 사실이지만, **진짜 원인은 메모리가 아니라 컨텍스트 스위칭과 스케줄러 부하**다. 원인을 틀리게 짚으면 처방도 흔들린다. (이 경우 결론은 우연히 같았지만.)

### 4-4. 옛 경로가 암묵적으로 제공하던 것을 잃었다

브로드캐스트를 걷어내면서 **주기적 heartbeat가 함께 사라졌다.** 새 폴링 루프는 값이 변경됐을 때만 전송하므로, WARD 앱이 꺼져 있거나 캐시 TTL이 만료되면 아무것도 나가지 않는다.

그러면 nginx의 `proxy_read_timeout`(당시 60초)에 걸려 연결이 끊긴다. 조용한 상황에서만 재현되는, **찾기 어려운 회귀**였다.

> 교훈: 경로를 교체할 때는 옛 경로가 명시적으로 하던 일뿐 아니라 **부수적으로 보장하던 것**까지 목록화한다. heartbeat는 어느 코드에도 "heartbeat"라고 적혀 있지 않았다.

### 4-5. 부하 테스트 규모가 필요 대비 100배였다

2000 동시 연결로 테스트했지만, 실제 MVP 목표는 사용자 100명, 피크 동시 접속 20명 수준이다.

한계를 미리 아는 것 자체는 가치가 있다. 다만 **그 테스트에서 나온 과제(가상 스레드 전환)보다, 추론으로 발견한 과제(heartbeat 회귀, 클라이언트 재연결 부재)가 실제 서비스에는 훨씬 치명적이었다.** 후자는 사용자 10명에서도 100% 재현된다.

> 교훈: 부하 테스트는 "언제 죽는지"를 알려주지만 "지금 틀렸는지"는 알려주지 않는다. 둘은 다른 질문이다.

## 5. 현재 규모에서의 타당성

|항목|MVP 실측 예상|여유|
|---|---|---|
|동시 SSE 연결|~20|—|
|Redis GET|20/초|Redis 처리량의 0.02%|
|폴링 스레드|20개|무시 가능|
|추가 메모리|~2MB|무시 가능|

**현재 구조는 이 규모에 적합하다.** 가상 스레드 전환은 한 줄이므로 해두어 나쁠 것은 없지만, 지금 병목이 아니다.

확장이 필요해지는 시점의 신호는 **연결 수**이지 사용자 수가 아니다. 동시 연결이 수백 단위로 올라가면 공유 스케줄러 폴링(스레드 O(1), Redis 왕복 1회) 또는 pub/sub으로 옮긴다. 읽기 경로만 교체하면 되므로 이행 비용은 낮다.

## 6. 예상 질문과 답변

**Q. 왜 브로드캐스트에서 폴링으로 바꿨나요?**

> 인프로세스 이벤트 버스를 쓰고 있어서 인스턴스가 2대 이상이면 다른 인스턴스에 붙은 보호자에게 위치가 전달되지 않았습니다. 에러 없이 조용히 실패하는 종류라 더 위험했고요. 공유 저장소를 보는 구조로 바꿔서 인스턴스 경계를 없앴습니다.

**Q. 워커 스레드 점유 문제 때문이라면 `@Async` 한 줄이면 되지 않나요?**

> 맞습니다. 그것만이 이유였다면 전환은 과했습니다. `@Async`는 스레드 문제만 풀고 인스턴스 경계 문제는 못 풉니다. 전환의 진짜 근거는 후자였고, 워커 점유는 부차적이었습니다.

**Q. pub/sub이 더 효율적이지 않나요?**

> 비용 면에서는 그렇습니다. 이벤트 기반이라 헛돌지 않고 연결당 스레드도 필요 없습니다. 폴링을 택한 건 구독자 생명주기 관리와 재구독 로직이 없어서 MVP에서 운영이 단순하기 때문입니다. 동시 20 연결 수준에서는 비용 차이가 무의미했고, 읽기 경로만 바꾸면 되니 나중에 옮기는 비용도 낮다고 판단했습니다.

**Q. 상시 폴링이 낭비 아닌가요?**

> 낭비 맞습니다. GPS가 30초 주기인데 1초마다 조회하니 30번 중 29번은 값이 그대로입니다. 대신 갱신 지연이 1초 이내로 들어옵니다. 30초 폴링이면 평균 15초 늦게 뜨고요. 현재 규모에서는 Redis 부하가 무시 가능한 수준이라 이 교환이 유리하다고 봤습니다. 연결이 수백 개가 되면 재검토할 항목입니다.

**Q. 이 전환에서 가장 아쉬운 점은?**

> 두 가지입니다. 하나는 전환 이유를 처음에 잘못 짚었던 것 — 워커 점유를 주된 근거로 봤는데 실제 결정적 이유는 인스턴스 정합성이었습니다. 다른 하나는 브로드캐스트를 걷어내면서 heartbeat가 같이 사라진 걸 뒤늦게 발견한 것입니다. 어느 코드에도 heartbeat라고 적혀 있지 않아서, 옛 경로가 암묵적으로 보장하던 걸 목록화하지 않은 대가였습니다.

**Q. `SseEmitter`는 스레드를 점유하나요?**

> 아닙니다. 컨트롤러가 `SseEmitter`를 반환하면 Spring MVC가 서블릿 비동기 모드로 전환해서 Tomcat 요청 스레드를 즉시 반납합니다. `SseEmitter`는 살아있는 응답에 대한 쓰기 핸들이고, 연결 자체는 커널 소켓과 Tomcat NIO가 들고 있습니다. 다만 누군가 `send()`를 호출해줘야 하는데, push 구조에서는 이벤트를 처리하는 스레드가 그 역할을 하고 pull 구조에서는 우리가 띄운 폴링 스레드가 합니다.

|---|---|---|
|가상 스레드 전환|낮음|한 줄이지만 현재 규모에서 병목 아님|
|공유 스케줄러 또는 pub/sub|낮음|동시 연결 수백 단위 도달 시|

마지막 항목이 중요하다. **전환의 근거가 "멀티 인스턴스에서 동작한다"인데, 아직 2대로 띄워 검증하지 않았다면 그 근거는 아직 가설이다.**
