
  
## 0. 논의의 발단  
  
두 가지가 동시에 걸렸다.  
  
1. `gps_histories`는 **매일 꾸준히 쌓이는 append-only 테이블**인데, 앞으로 조회 주체가 둘로 늘어난다. **사용자(보호자의 경로 조회)와 룰엔진(이상이동 판정의 윈도우 조회).**
2. 위치 정보는 무기한 보관할 수 없다. 일정 기간이 지나면 지워야 하는데 **삭제 정책도, 삭제 수단도 없다.**  
  
조회 최적화와 보관 정책은 별개 문제처럼 보이지만, Postgres에서는 파티셔닝이라는 한 가지 수단이 양쪽에 동시에 걸린다. 그래서 같이 다룬다.  
  
## 인덱스 도입 

### 배경

gps_histories는 GPS를 30초마다 받아 하루 2,880행씩 사용자마다 쌓이는 테이블이다. 여기에 조회 주체가 둘 붙는다. 보호자의 일자별 경로 조회와, Isolation Forest 기반 이상탐지 배치의 주 단위 궤적 조회다.
또한, 위치 이력 3개월 단위로 제거할때 풀스캔을 하고 delete 하게 된다. 이것또한 인덱스 스캔으로 조회 시간을 줄여야한다.

30명이 30초 주기로 90일동안 위치 좌표를 받는다.
총 : 7,776,000건 적재 (약 996MB)

shared_buffers 는 256MB라 90일동안의 좌표가 캐시에 들어가지 못해, 조회를 반복해도 매번 디스크에서 읽어야함
### 쿼리문

```sql
SELECT *  
FROM gps_histories  
WHERE  
    ward_member_key = 'SEED0001-0000-4000-8000-000000000000' 
    AND recorded_at >= '2026-07-31 00:00:00'                 
	AND recorded_at <  '2026-08-01 00:00:00'                 
ORDER BY  
    recorded_at ASC;
```

### 인덱스 생성 후
#### 인덱스 구성 
[memberKey, recordedAt]
- 동등조건인 memberKey를 선행컬럼으로 두고 범위 조건인 recorded_at을 후행 컬럼으로 두면, memberKey를 기준으로 수직탐색후, recordedAt으로 수평 탐색
- 선행 컬럼이 등치, 후행이 범위이자 정렬 키라 `ORDER BY recorded_at`의 별도 sort까지 제거된다.

## 파티셔닝 도입 전과 후

### DELETE 쿼리 실행

#### 도입 전 상황

단일 테이블 상황에서 770만 데이터 중 3개월이 지난 데이터를 매달 삭제해야한다.
삭제 시  걸리는 총 시간을 구해본다.

쿼리 시간 : 14초
삭제 전후 테이블 크기 줄어들지 않음 : postgreSQL은 파일의 뒤쪽 오래된 데이터부터 지우기 때문.
- dead tuple이 다량 발생 (DELETE는 행마다 '죽었음' 표시)
- 공간을 실제로 반환하는 수단은 VACUUM FULL인데, 테이블 전체에 락을 걸어 다른 기능이 마비된다.
- 즉, 단일 테이블 구조에서 디스크를 되찾을 수단이 존재하지 않는다.

#### 도입 후 상황
- DELETE 대신 DROP PARTITION 명령어로 해당 기간의 파티션을 통째로 삭제
- 트랜잭션 로그를 남기지 않고 메타데이터만 삭제
- DROP TABLE은 파일을 통째로 삭제하는것이기 때문에 dead tuuple이 발생하지 않음

쿼리 시간 : 45.8ms
